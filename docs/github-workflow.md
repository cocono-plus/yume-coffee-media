# GitHubの保存・一括反映手順

## 毎回の終了点

1. 最新mainのAGENTS.mdと対象手順、現在の指示を確認し、対象・完成条件・終了点を決める。通常制作/リライト/修正は「作業ブランチ保存」、明示された場合だけ「Draft PR」「main」「本番公開」とする。既存の明示公開指示は維持する。
2. 現在のブランチ・未保存差分・既存PR・同時進行作業を確認する。既存フォルダをreset/restore/上書きせず、記事専用環境等の既存分離方式を守る。
3. 本文・対象画像・参照先・必要な生成データを既存ルールどおり整え、対象範囲、秘密/非公開資料、型・テスト・buildを必要な範囲で検証する。未実施・失敗・仮画像と実採用を区別する。
4. 指定した対象ファイルだけをコミットし、PRのない専用作業ブランチへpushする。remoteの先端SHAを読み返して照合する。途中保存は途中保存、検証未完了は未完了と報告し、完成と偽らない。
5. 保存ブランチ、commit SHA、変更対象、検証結果、残件、PR/main/公開の実施状態を短く報告して終了する。「完成」は記事品質の結果であり、本番公開済みを意味しない。

## まとめて反映する指示を受けたとき

- 完成済みブランチと各SHA・対象記事/機能を一覧にし、同じリリース対象だけを最新mainからの統合ブランチへ取り込む。別リポジトリを1つのPRに混ぜない。未完成・別依頼・非公開資料・他人の作業を混入させない。
- 共有ファイル、記事番号、URL、画像名、カタログ/SQLの競合を調整し、統合後の最終差分に対して必要な検査を再実行する。機械的な全branch mergeや自動生成ファイルの上書きで解決しない。
- PRを依頼された段階で原則1つのDraft PRを作り、元ブランチ/SHA・対象・検査結果を記録する。既存PRを照合し重複作成しない。複数記事に未対応の専用取り込みツールを、ガード解除で通さない。
- main反映まで指示された場合はリポジトリの正規取り込み手順を使う。PRのready化が必要なら既存手順に従うが、PRの承認操作を代行しない。mainを読み返して対象SHAと差分を確認する。
- 本番公開まで指示された場合だけ、対象main SHAを固定して既存の公開経路を1回実行し結果を確認する。公開の失敗/未確認/公開済み警告を区別し、結果不明のdispatchやuploadを盲目的に繰り返さない。

## Actionsを無駄に増やさない

作業ブランチへの保存とPR作成は別工程。Draft PRでもpull_requestの検証は起動する。PR作成後の追加pushも検証を起動し得るため、小修正はローカルで検証してまとめて保存する。既存PRを勝手に閉じたり、そのブランチをforce-pushしない。発火条件は実際の.github/workflowsと外部連携で確認し、「全branch pushは無料」と一般化しない。

同じ最終SHAに成功した必要検証があれば、結果を確認して不要な再実行を避ける。ただし統合後の差分・依存・baseが変われば再検証する。取り込みworkflow自身が同じ実検査を行う場合、別実行のdry-runを機械的に毎回追加しない。安全検査・保護・認証・予算を無効化しない。

## 保全と適用範囲

この手順は今後このリポジトリを扱う各環境に適用する。開始・再開時に最新mainの本書とAGENTS.mdを読む。古いcheckoutは未保存作業を保全し、必要な手順差分だけを取り込む。ローカルフォルダ、クラウド環境の設定、他チャットの進行中作業が自動更新されたとは扱わない。

未公開の完成記事・原稿・画像・制作記録は削除しない。保存済みだけで公開済み/完了済みの容量整理条件を満たしたと扱わない。機密・人物参照・新規未採用原稿の非公開保存条件は各サイトの既存規則を優先する。
